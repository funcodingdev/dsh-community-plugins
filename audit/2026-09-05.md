## 1. [P1] 分组停用可以绕过宿主基础设施保护

位置：`src/routes.ts:1485-1487`；成员准入逻辑 `src/groups.ts:87-92`。单插件保护位于 `src/routes.ts:1305` 附近。

触发：某个受保护的宿主包在 profile dependencies 中，将它加入分组后停用分组。

复现中，同一个 `@deepseek-ai/dsh-host-web` 经单插件 `/toggle` 返回 403；经 `/groups` 创建、加入成员、停用，返回 200，且对应 loader entry 的 fiber 已被移除。

原因：分组成员过滤仅排除插件管理器自身；执行时直接调用 `setPluginEnabled`，没有调用 `isProtectedModule`。这使单插件入口明确禁止的动作仍能通过分组执行。若实际目标承担 Web 服务、热加载或存储功能，会中断宿主能力。

建议：在分组成员准入和执行阶段都检查保护规则；执行阶段必须覆盖历史保存的分组，并在发生任何成员变更前完成整组校验。

## 2. [P1] 回滚绕过正在运行的 agent 检查

位置：`src/routes.ts:2833-2865`。

触发：安装产生兼容性提示和有效回滚 token，随后 agent 开始运行，用户点击回滚。

复现中，在同一个正在运行的 `main` agent 状态下，普通卸载返回 409；安装回滚却返回 200，执行了 remove，且插件从临时 profile 中消失。

原因：回滚验证了操作锁、token 和 profile 快照，但没有检查 `runningAgentsForGuard()`。安装回滚会删除文件，更新回滚会重新安装旧版本，仍然具有普通安装/更新/卸载所防范的“agent 工作期间文件被替换”问题。公共 v1 回滚入口复用此处理器，也受影响。

建议：在持有操作锁、执行任何文件变更前检查正在运行的 agent；拒绝时保留 token，允许 agent 结束后重试。

## 3. [P2] 分组操作没有进入共享操作锁

位置：`src/routes.ts:1452-1507`；共享锁实现 `src/routes.ts:396` 附近。

触发：一次插件更新尚未完成，同时通过另一个请求停用该插件所在分组。

复现中，将 FakeDsh 更新命令保持在执行中，再调用分组停用，得到 200 而不是其他变更入口使用的 409；分组操作在更新持锁期间完成。

原因：整个 `/groups` 处理器都没有调用 `withMutationLock`。成员循环包含 await，可以与安装、卸载、回滚以及单插件启停交错，对 live mount、disabled 状态和回滚 token 产生互相覆盖。测试确认了并发执行，未声称已经复现具体文件损坏。

建议：所有分组变更统一进入共享写锁，并在锁内读取已安装成员与校验请求。避免在执行单成员逻辑时再次获取同一把锁。

## 4. [P2] 分组启用不清除单插件停用留下的持久化补丁

位置：`src/routes.ts:1485-1494`；单插件的补丁处理位于 `src/routes.ts:1327-1370` 附近。

触发：先单独停用一个具有 bundle patch 的插件，再通过分组开关启用它。

复现使用真实临时 YAML 文件：单独停用后 `/installed.patchDisabled` 包含 `dsh-loop`；分组启用虽然返回 200，该字段仍包含 `dsh-loop`。因此页面重新取数后仍会视它为停用，后续补丁重组/重启也会重新应用原先的禁用规则。

原因：分组只更新 live 状态和 state.json，没有执行单插件入口的 `enableRow`/`disableRow`。它也没有复用 disable-carrier 对 bundles 列表的维护逻辑，后者是相邻的同类检查缺口，但没有另外计为已复现问题。

建议：提取一个统一的单插件状态变更服务，包含保护检查、live 状态、state.json、用户补丁和 carrier bundles 处理，供单个与分组入口共同调用。

## 5. [P2] 取消 pnpm 自动重建后，取消结果被丢弃

位置：`src/install.ts:105-106`。

触发：安装遇到 `ERR_PNPM_PUBLIC_HOIST_PATTERN_DIFF`，进入自动 `pnpm install --no-frozen-lockfile` 重建；用户在重建期间取消。

复现：首个命令返回 hoist 错误，重建返回 `cancelled: true`。最终函数却返回 `cancelled: false`，还额外调用一次 store 清理命令（总调用数为 3，而不是 2）。

原因：只有重建成功时才更新 `result`，重建失败或取消时继续保留第一条命令的错误。调用方因此会把用户取消当作普通失败，进入本来应跳过的清理/失败回滚流程；重建的真实错误信息同样会被旧错误掩盖。

建议：重建不成功时采用重建结果，取消时立即返回；需要保留初始原因时使用独立字段或附加上下文，不覆盖取消状态。

## 6. [P2] 当前页面安装请求断线后，任务面板永久保留“安装中”

位置：`src/client/PluginHubSection.tsx:1308-1317`；同类更新分支 `1340-1349`。

触发：在当前页面发起安装，HTTP 连接断开，但后端继续完成安装，随后状态轮询确认插件已安装。

复现使用真实 React 组件：`dsph-pending` 已清空，插件状态已恢复，任务面板入口仍显示旋转的 `Installing 1/1`。此时轮询随 `busyUrl` 清空而停止，残留记录没有后续收敛机会。

原因：轮询只删除 `recoveredInstall.current` 指向的、重新打开页面时创建的任务；当前页面的 `recordId` 只在 `doInstall` 闭包中，断线 catch 不处理它。已有断线测试只检查 session marker 与错误提示，未检查任务面板是否结束。更新代码同样仅清理 recovered id，但本次动态复现针对安装流程。

建议：统一保存当前操作 id，正常响应和状态轮询都通过同一个完成函数更新任务记录。若轮询无法确定真实结果，应显示“结果待确认”，不能一直保留运行中或仅凭依赖存在宣称完整成功。
